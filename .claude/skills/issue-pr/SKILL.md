# 이슈 → PR

인자로 받은 이슈 번호를 `N` 이라 한다.

## ⛔ 이 스킬의 절대 규칙

**상태를 바꾸는 모든 단계에서 멈추고 승인을 받는다.** 이 스킬을 호출했다는 것은
"작업 절차를 따르라"는 뜻이지, "끝까지 알아서 진행하라"는 뜻이 아니다.

승인 없이 진행 금지: 파일 생성·수정·삭제, 브랜치 생성, `git add`/`commit`/`push`,
PR 생성·머지, 이슈 수정, 컨테이너·서버 기동.

조사·조회는 승인 없이 해도 된다: `gh issue view`, `git status`, `git log`, 파일 읽기.

## 작업 등급 — 무엇을 대신하고 무엇을 넘기는가

| 등급 | 대상 | 방식 |
|---|---|---|
| A | 인프라 · DB · 배포 · 서버 | 설명만 하고 **사용자가 직접 실행** |
| A | 핵심 설계 (공통 에러, `as_of` 계층, LLM 프롬프트) | 같이 설계하고 사용자가 구현 |
| B | 엔티티 · API · 배치 | 작성하되 **줄 단위로 근거를 설명**하고 되짚는다 |
| C | 시드 데이터 · 반복 CRUD · 테스트 보일러플레이트 | 작성하고 결과만 확인 |

"일단 이렇게 하면 됩니다" 하고 넘어가지 않는다. 사용자가 설명하지 못하는 코드는
남기지 않는다.

## 1. 이슈를 읽는다

```bash
gh issue view N
```

**작업 내용** 체크리스트와 **인수 조건** 을 그대로 옮겨 적는다. 인수 조건은
나중에 검증표가 되므로 빠뜨리지 않는다.

체크리스트가 5개를 넘으면 **단계로 쪼개서 제안한다.** 각 단계가 끝날 때마다
동작을 확인할 수 있게 나눈다. 중간에 멈춰도 진척이 남는다.

**⛔ 여기서 멈추고 단계 계획을 승인받는다.**

## 2. 브랜치

```bash
git checkout develop && git pull
git checkout -b feature/N-<영문-설명>
```

예) `feature/2-glossary-term-entity`

**⛔ 브랜치 생성 전에 승인받는다.**

## 3. 작업 · 커밋

Conventional Commits — `feat` `fix` `chore` `docs` `test` `refactor`

제목은 한 줄, 본문에 무엇을 왜 바꿨는지. 커밋을 잘게 나눌 필요는 없다.
어차피 squash merge 다.

**⛔ 파일을 만들기 전에 무엇을 왜 만드는지 설명하고 승인받는다.**
**⛔ 커밋 메시지 초안을 보여주고 승인받은 뒤 커밋한다.**

## 4. 인수 조건을 실제로 검증한다

"될 것 같다" 로 넘어가지 않는다. 명령을 직접 실행하고 결과를 기록한다.

```bash
docker compose up -d
./gradlew bootRun     # 서버가 뜨는지
./gradlew test        # 테스트가 통과하는지
```

인프라 명령은 **사용자가 직접 실행한다.** 결과를 같이 읽는다.

각 인수 조건에 대해 실행한 명령과 실제 출력을 남긴다. 이게 PR 본문의
검증표가 된다.

## 5. PR

```bash
gh pr create --base develop
```

본문은 네 부분으로 쓴다:

```markdown
## 무엇을
바뀐 것들을 목록으로.

## 왜 이렇게 했는지
**가장 중요한 부분.** 선택지가 있었던 지점마다, 왜 이쪽을 골랐고
다른 쪽은 왜 아닌지. 나중에 이 결정을 되짚을 사람은 나 자신이다.

## 어떻게 검증했는지
| 인수 조건 | 결과 |
|---|---|
| ... | ✅ 실제 출력 |

## 남은 항목
이 PR 에서 못 한 것과 그 이유.

Closes #N
```

**⛔ PR 본문 초안을 보여주고 승인받은 뒤 생성한다.**

설계 결정이 있었다면 노션 **의사결정 기록** 에도 남긴다.
(주식읽기 / 숨김페이지 / 회의·개발일지 / 🧭 의사결정 기록)
양식: `날짜 | 한 줄 요약` + 대안 / 선택 이유 / 트레이드오프

## 6. 머지

CI 통과를 확인하고 **Squash merge**.

> **PR 을 머지 없이 닫으면 브랜치의 작업이 통째로 사라진다.**
> 2026-09-09 에 PR #50 을 닫고 브랜치를 지워 초기 세팅 8개 파일이 사라졌다.
> 이때는 사용자가 명시적으로 되돌리기를 요청한 의도된 폐기였지만,
> 실수로 같은 일이 벌어지면 복구가 번거롭다.
> 방향을 바꾸고 싶으면 브랜치에 커밋을 더 쌓아 PR 을 갱신한다.

**⛔ 머지 전에 승인받는다.**

## 7. 정리

```bash
git checkout develop && git pull
git branch -d feature/N-<설명>
```

이슈는 `Closes #N` 으로 자동으로 닫힌다.
